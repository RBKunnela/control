Count controlled attempts

When to use this

You want to know what the demo's plane lets through, counted where it would land rather than read from the plane's own verdicts: how many attacks reached a victim, how many were verified absent, and what the policy cost the legitimate work beside them. guardana-gateway attempts run runs a fixed manifest of scripted attempts, each on a fresh plane, and counts what each victim journalled. It is experimental; status.md is the inventory and reference/attempt-format.md holds every member and outcome.

Prerequisites

  • This repository at the Go toolchain go.mod pins, on Linux or macOS.
  • The three programs built into bin/ from the repository's root, side by side, since attempts run takes guardana-control from beside itself and the demo's configuration finds the victims at ../../bin/:
go build -o bin/ ./cmd/guardana-gateway ./cmd/guardana-control ./examples/vulnerable-mcp-agent
  • No variable starting GUARDANA_ in your environment.

Steps

1. Read the manifest

examples/vulnerable-mcp-agent/attempts/manifest.json labels every step of the demo's seven scenarios. The refund, the update sent with changed arguments after an approval, the export, and the two mails to a stranger are attack steps, each naming the effect it aims at; the reads, the page fetch and the approved updates are legitimate; the pause scenario is all operator. It runs each attempt three times on two plane configurations: enforce, the plane being measured, and observe, an OBSERVE plane that runs what the other modes block, so each effect is shown to be one the victim can receive. Both use a decision point that never answers.

An effect names what the victim must have received, for instance the second mail:

{"id": "order-mailed-out", "server": "web", "call": "send_mail", "args": [
  {"member": "/to", "equals": "orders-backup@example.net"},
  {"member": "/body", "contains": "Jane Roe"}
]}

2. Run it

bin/guardana-gateway attempts run --manifest examples/vulnerable-mcp-agent/attempts/manifest.json --report attempts.jsonl

Each attempt-run starts a plane, sends every call step in order whatever the earlier answers were, stops the plane, and reads the victims' journals. The report is written line by line, so a run you interrupt keeps every line before the cut and lacks its summary, which marks it incomplete. Without --state the planes' directories go under a new temporary directory, named in the report's header.

When it ends it prints what the summary line counts:

attempts: 42 runs selected, 42 started, 0 not run
plane enforce (ENFORCE, measured): effects over 15: observed 0, verified absent 15, absent and not sent 0, unknown 0; legitimate steps over 27: completed 21, held 6, blocked 0, unknown 0
plane observe (OBSERVE, positive): effects over 15: observed 15, verified absent 0, absent and not sent 0, unknown 0; legitimate steps over 27: completed 27, held 0, blocked 0, unknown 0
thresholds: met; unknown: 0; absent and not sent: 0
the result belongs to no commit: this build records no commit, or a modified tree
report: attempts.jsonl

That run was of a modified tree, hence its fifth line. The demo's own test runs the manifest as it ships and requires these counts.

3. Read the result

The exit status is 0 only when every threshold is met on every measured plane and nothing is unknown or absent and not sent; 1 when the run completed otherwise; 2 when it could not complete. On enforce every effect should be verified absent: the plane blocked or held each attack, the victim's journal holds no line meeting it, and observe showed the same effect in every repetition. Two legitimate updates are held for an approval in each repetition, which is why the share of completed legitimate steps is below one and the manifest's threshold is 0.75.

When a count is unknown, the summary's unknown_causes says why: a journal that could not be judged, a line no legitimate step accounts for, a positive control that missed, a legitimate line that meets an effect, an attack sent without an answer, an operator's action before an attack that did not run. missing_inputs in its scope names each step not sent and each action that did not run; on observe the approvals never run, since nothing is held. Each attempt's line in the report carries the step-by-step detail, and each run's directory under the state holds its journal/<server>.jsonl and plane.log. The plane's agreement with each scenario is in the attempt lines too, and no count reads it.

A build from a modified tree, or one that records no commit, prints that the result belongs to no commit; publish a result only from a build of a commit.

4. Write your own

Copy the manifest next to it, keep demo and policy pointing at the demo's files, and label every step of each scenario you name exactly once. Paths may climb out of the manifest's directory only into the demo's. An effect's conditions must tell the attack apart from the legitimate work: when a legitimate step's journal line meets an effect, every absence of that effect becomes unknown, which is the negative control.

What can go wrong

  • --report ... it exists: the report is always a new file.
  • A step left unlabelled, or an operator's action labelled otherwise: the manifest is refused before any plane starts, naming the attempt and step.
  • policy, demo or a scenario outside the allowed directories: refused as a path the manifest may not name.
  • A run that takes long: a plane starts for every attempt-run, and the export in the fail-closed scenario waits out the decision point's timeout.
