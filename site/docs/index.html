Documentation

Rendered from every page's own frontmatter and from the records. Rebuild it with make docs-gen; an edit made here does not survive the next run.

Get started

  • Try the demo: Start a plane in front of two vulnerable MCP servers, answer a held call, pause a server, read the trail and the counters, and run the demo's scenarios.

Guides

  • Connect an existing MCP setup: Put the plane between an MCP client and a server you already use, classify the server's tools, hold its writes for approval, and end in a local report.
  • Decide a tool of your own: Serve the enforcement API, classify your tools by name, and have a client ask before each call and report how it ended, under one policy and trail.
  • Keep two tasks apart: Open a run per task in a runs directory, point a plane at it, and give each agent its token, so what one task took in never decides another's calls.
  • Let a decision point veto calls: Point the gateway at an AuthZEN decision point, write the two rules that let it veto a scope, test what each answer does, and check the plane before it serves.
  • Read the evidence from a program: Export a trail file in the versioned format, resume where the last export stopped, and rebuild each call's lifecycle without importing the project's internals.
  • Run the gateway in a container: Run the release image of the gateway with Docker, with its evidence on a volume and its port reachable from the host alone.
  • Run the gateway: Set up a plane's policy files, start the MCP gateway in OBSERVE, keep its policy confirmed, read its health, classify the tools it sees, and move it to ENFORCE.
  • Supervise and stop a run: Run the refund example by hand on a live plane, supervise the run against its procedure, read its page, and stop it on a confirmed finding.
  • Test a procedure: Lint a procedure document, then prove what supervise finds with cases that state a run, its evidence and every expected finding.
  • Watch a plane without a collector: Run the collector the gateway binary ships, point a plane's export at it, and check each request's trail in the file it writes.
  • Write and test a policy: Write an agent-policy/v1alpha1 document, lint it, prove what it decides with cases, sign it into the bundle a plane loads, and vouch that the bundle is current.

Concepts

  • Approvals and the held request: What the enforcement point holds when a call needs an approval, what a retry must equal to resume it, and the ways a hold ends.
  • Architecture: The system in context, its containers, the request path from a proposed action to a decision and its evidence, the dependency rule, and where it is going.
  • Control and supervision: The 1.0 goal for connected observation, procedure checks and scoped reactions, with today's alpha and the three API roles kept explicit.
  • Enforcement modes: What each mode does with the kernel's decision, what it needs from an adapter, and which modes this build runs.
  • Evidence and the spool: The trail every call leaves, the order its events may take, and how the spool keeps them on disk before an exporter sees them.
  • Glossary: One name per concept, as the pages and the code use it, with the symbol or path that defines each.
  • How a call is decided: From a proposed action to one of five verdicts and the action enforced for it, including what happens when the kernel cannot decide.
  • The MCP gateway: How a tools/call becomes a decision, an authorized set of bytes and a trail, before the server sees it.
  • Observations, coverage, supervision and a stop: How what a source reports, the coverage map, the supervisor's findings and a stop of one run fit together, and what each promises and does not.
  • Privacy: What the plane records about a call, where each record goes and who can read it, how long it stays, and that nothing goes to the project.
  • Threat model: What the plane protects, from whom, what it does about each attacker today with the code and the test behind it, and where it stops.

Reference

  • Benchmarks: What three calls on the authorization path and one tool call through the gateway cost on one machine, how they are measured, and what the numbers are not.
  • Claude Code hooks: What the claude-code hook profile covers, the hook settings it needs, what the bridge reads and answers per event, and the gaps it leaves.
  • Command line: The two binaries, what each prints as its help, and the exit statuses they share.
  • Configuration: Every key the gateway reads, with its environment variable, kind, default, whether it is required and the spellings it takes.
  • The approvals page: What guardana-control console serves, what it prints, what it refuses and what it cannot tell you.
  • Coverage: What guardana-control coverage reads, the inventory it takes, the state it gives each declared path, the join with a plane's evidence, and its exit status.
  • Dev mode: What guardana-gateway dev lays out, refuses, prints and stops, and how --scenario runs each scenario on a plane of its own.
  • Failure modes: What a plane does when its collector, spool, decision point, upstream, pause file, stop list, freshness statement or clock fails, or it is killed holding calls.
  • MCP enforcement coverage: Per revision, transport and method, what the gateway enforces today and what it does not.
  • Metrics: Every metric a plane answers on /metrics, with its type, its label, the statistic it reads and what it counts.
  • Obligations: The catalogue of obligation types a policy rule may name, the parameters each takes, and what the tree does with one.
  • Observations: The source descriptor, what an import of OpenTelemetry GenAI spans keeps and drops, the observation log and its export.
  • Policy explain: What guardana-control policy explain reads, every line it prints, which rule decided and which input a rule could not read, and its bounds.
  • Policy document format: Every member of an agent-policy/v1alpha1 document, the values each admits, the bounds, and the members of a policy test case.
  • Reaction: The signed route, the stop list and the commands that write them, and how a plane refuses a stopped run's calls and reports its stops.
  • Reason codes: Every reason code a decision may carry, with its number and the verdict it usually accompanies.
  • Run view: The page guardana-control supervise --view draws for one run, what each mark on it means, and what the command refuses to overwrite.
  • Runs: The runs directory, what runs open, close and list print and refuse, and what a plane with runs.dir does with a token.
  • Scenario format: Every member of an agent-scenario/v1alpha1 document, how scenario run holds a live plane to one, and what it exits with.
  • Starter policy packs: The read-only and approval-for-writes packs, what each decides, what it assumes about the plane, the cases that prove it, and what it leaves unguarded.
  • Supervision: The procedure document, what guardana-control supervise checks for one opened run, the finding record and its log, and how notify delivers findings.
  • Format versions: Every versioned file and message a user writes or reads, the version this tree writes, the versions it reads, and how stable each is.
  • action_envelope.proto: The messages and enums of action_envelope.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • approval.proto: The messages and enums of approval.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • bundle.proto: The messages and enums of bundle.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • common.proto: The messages and enums of common.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • decision.proto: The messages and enums of decision.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • event.proto: The messages and enums of event.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • finding.proto: The messages and enums of finding.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
  • result.proto: The messages and enums of result.proto as the compiled descriptor declares them, each field with its number, cardinality and type.
