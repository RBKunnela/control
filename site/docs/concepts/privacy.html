Privacy

The plane records what a call was about, not what it said. A tool call's arguments and its result are recorded as hashes; the one piece of argument text that can enter a record is a resource id the operator told the plane to read out of them. A tool outside MCP may also report a side effect's confirmation, such as a receipt number, and it is recorded as sent, at most 1024 bytes. A resource read's URI and a prompt's name are recorded as the agent sent them. Nothing turns content capture on in this build, and hidden model reasoning is never stored (ADR-0004, invariant 9). What the plane defends against is on the threat model page.

What an evidence event holds

Every call the plane can name leaves a trail of events (evidence), with three exceptions: a read the operator lets run unrecorded when the spool cannot take its events (evidence.on_unwritable: allow_reads), a call refused because its request id already has an open trail, and a call blocked because the sink refused its first event. The MCP adapter and the pipeline fill them as below (adapters/mcp/translate.go, adapters/mcp/answer.go, internal/evidence/event.go).

Every event carries event_id, kind, request_id, project_id, tenant_id, occurred_at, schema_version, the plane's enforcement_mode, prev_event_id and, where the call belongs to a run, run_id, an id the plane mints or, under runs.dir, the id of the run the operator opened. execution_id is on the events of a call handed to execution. prev_event_digest is left empty.

ACTION_PROPOSED carries the envelope:

Field What this plane puts there
request_id, occurred_at, project_id, tenant_id, environment an id the plane mints, the clock, and the configuration
principal id, type and tenant_id from listener.principal, the plane's tenant_id when it names none; no end user, since no key wires an authenticator
agent id, framework and version from listener.agent
action kind (tool, resource or prompt), name (the tool's name, the resource's URI or the prompt's name), protocol mcp, the effect class, and provider, the upstream's name
resource the override's type, and id: the string or number at the override's resource_from pointer into the arguments, none for another value, the URI of a resources/read, or the name of a prompts/get; the upstream's tenant_id and environment. An action name or resource id refused as over-long is recorded as overlong:sha256: and the hex SHA-256 of what was sent, and a called tool name, prompt name or resource URI that quotes a credential the plane holds, cannot be scanned or starts with withheld:sha256: is recorded as that prefix and the hex SHA-256 of it, in the action name and, for a read, the resource id; the upstream receives it as called
destination the override's trust zone, when it names one
arguments canonical_hash only: a SHA-256 of the canonical arguments
trace_id, span_id the trace id and the parent id of a version 00 traceparent in the request's _meta, the client's claim; empty without one
context.tags mcp.client= with the name and version the client reported, mcp.protocol_version=, and the plane's flow tags: whether the run took in untrusted content, and the highest sensitivity it read, or flow.v1.state=uncomputed when the plane kept no run state for the call

Left empty by this plane: principal.authn_strength and attributes, agent.instance_id and model_ref, delegation, resource.labels, destination.host, data, arguments.redacted_preview, schema_ref and redaction_profile, and every other context field.

POLICY_DECIDED and ACTION_BLOCKED carry a decision: the verdict, the reason codes, the ids of the rules that matched, the obligations as the policy wrote them, the action digest, the bundle digest, timings, and, when a decision point was asked, its identifier. On a block of the enforcement point's own, ACTION_BLOCKED carries that point's decision instead: the same digests, and no rule ids, obligations or identifier.

APPROVAL_REQUESTED, APPROVAL_DECIDED and APPROVAL_EXPIRED carry the approval: its ids, the action digest, the bundle digest, its state and times, and on an answer the approver_id and the optional --reason exactly as the approver typed them.

ACTION_STARTED carries no payload. ACTION_COMPLETED and ACTION_FAILED carry the result: its status, when it started and ended, the protocol's own status (ok, isError, input_required for an upstream that asked for input, timeout, error, unhashable for a result that cannot be encoded, whose status is then UNKNOWN, or a JSON-RPC error code, each after withheld: when the answer quoted a credential the plane sends and the agent was given a fixed answer instead), a SHA-256 of the result's JSON encoding when there was one, and the digest of the bytes that were sent. Neither an error message from the upstream nor any part of the result is kept (resultOf in adapters/mcp/answer.go). An ACTION_FAILED for a call that was never sent carries the status BLOCKED and the code that stopped it, and no digest of sent bytes.

This plane writes no POLICY_RELOADED and no FINDING_RAISED.

A hash is not anonymity. Arguments or a result with few possible values, such as a month or a yes, can be recovered by hashing each guess and comparing.

Capture and reasoning

ADR-0004 lets an operator opt in to capturing content. This build has no setting for it: the MCP adapter builds the arguments message with the hash alone, the authorized envelope clears any preview (internal/gateway/authorize.go), and the plane clears both previews and their profiles from every event it hands the sink, whatever an adapter set (uncapture in internal/gateway/trails.go). Capture is off, and nothing turns it on. The collector that collect runs clears the same fields from every event it receives before its trail holds it, so a previewed event another producer sends is not kept either (adapters/otel/receiver.go).

Hidden model reasoning is never stored at any setting. MCP does not carry it to the plane, no field of the contract holds it, and no adapter reads it.

Where records go, and who can read them

  • the plane's memory

    What
    a held request, its envelope and its decision; without runs.dir, the run state of each principal
    Who can read it
    the plane's process: a held request until its hold ends, a run's state until the plane stops

  • the runs directory, runs.dir

    What
    each run's record, its project, tenant, principal, agent, lifetime and the SHA-256 of its token's secret, and each root run's flow state
    Who can read it
    the operator's account, in a directory only it may write, until the operator removes them; under approvals.authority: signed, records/ is the operators', each record also naming its signer's key id and the records/ path, and state/ the plane's

  • the spool, evidence.dir

    What
    every event, one framed JSON line each, until a collector accepts it or it is moved to quarantine.log
    Who can read it
    the plane's account: new files are 0600; the directory must be the plane's account's and writable by no one else, and an existing segment or quarantine.log is refused when another account owns it or a group or others may write it

  • the collector at export.endpoint

    What
    every event, as the body of one OTLP log record, with its ids, kind and mode as attributes
    Who can read it
    whoever runs that collector and wherever it sends them; https, or a unix socket whose peer is export.collector_uid; never plaintext

  • the trail segments collect writes

    What
    every event the collector accepted, at least once
    Who can read it
    the account that ran collect: the directory is 0700 and each file 0600; a directory the group or others may reach, a file they may write, or either of another account is refused

  • the approvals directory

    What
    per held call, the approval record and a projection: principal, agent, tool, upstream, resource type and id, effect class, rule ids, times
    Who can read it
    the plane's account: records are 0600, and the directory is refused when another account owns it or others may write it; under approvals.authority: signed the plane writes them 0640 for an operators' group

  • the inbox, approvals.inbox_dir

    What
    per signed answer, the tenant, project, request and approval ids, both digests, the decision, its time, the optional reason and the signer's key id
    Who can read it
    the operators' group the directory admits; each answer is 0644

  • the approvals page and approvals list

    What
    the projection, and the approval's state, ids, digests, expiry and approver; no arguments, no preview, no trail
    Who can read it
    the page: whoever holds its session, on 127.0.0.1 (reference/console); approvals list: any account that can read the approvals directory

  • the hold journal, approvals.hold_journal_dir

    What
    per hold, the trail's ids, the binding, the approval and its expiry; no envelope and no decision
    Who can read it
    the plane's account: entries are 0600

  • the ledger, ledger/ in the hold journal's directory

    What
    per spent or settled approval, the binding, the request and approval ids, the approver id the plane recorded and when
    Who can read it
    the plane's account: marks are 0600

  • the floor directory, policy.state_dir

    What
    per bundle id, the serial, digest and issuedAt of the newest freshness statement taken, and the reason and prior value of the last reset
    Who can read it
    the plane's account: the directory is owner-only and its files 0600

  • the other floor directories, trust.floor_dir, pause.floor_dir, reaction.floor_dir and reaction.stops_floor_dir

    What
    the serial and digest of the newest roster, signed pause file, route and stop list header taken, with the tenant and project for the pause file and the stop list, and the length and digest of the stop list part accepted
    Who can read it
    the plane's account, as policy.state_dir

  • the trust roster, trust.roster

    What
    per operator key, its subject, public key and grants
    Who can read it
    any account the file's modes let read it

  • the pause file

    What
    each entry's scope and its optional reason; a signed one also the tenant, project, its path, serial and signer's key id
    Who can read it
    the plane's account, and any account the file's and directory's modes let read it; under approvals.authority: signed the operator's account, never the plane's

  • the stop list, reaction.stops

    What
    per stop the tenant, run id, finding id, procedure, rule and times, and under approvals.authority: signed its scope and subject, a run, agent or principal id; per covered finding its id, tenant and run, and under signed its scope and subject; per lift the run, or under signed the scope and subject, a line number and its signature
    Who can read it
    the plane's account, and any account the file's and directory's modes let read it: a new list is 0600, or 0640 under approvals.authority: signed, and the list is refused when another account owns it or its directory, or a group or others may write either; under signed it is refused when the plane's own account owns either, and its header and lifts also name the signing operator's key id, the project and the stop list's path

  • the decision point at pdp.identifier

    What
    the principal, the action, the resource with its id, the destination, the data labels and the ids; never the arguments, their hash or a digest
    Who can read it
    whoever runs it, and a proxy configured for it (ADR-0017)

  • /metrics and /healthz

    What
    counts and states; /healthz also the mode, the bundle's id, version, digest and serial, its confirmation and expiry times, the id of every pause entry with the share of calls it covers, the ids of those that match no listed tool, and a signed pause's serial and floor; with a route, also the route's id, serial and digest, its floor's serial and digest, the stop list's list_id, state, age and stop list header's serial, and how many stops are active, how many match no call of the plane (a run the runs directory does not hold for the plane's project, or an agent, principal or tenant other than the listener's) and how many have a run whose record cannot be read, as counts, never ids; health.socket adds, under approvals.authority: signed, the plane's plane_id, and the subject and key id that signed the pause and, for each active stop up to 64, its entry id, scope, subject (a run, agent or principal id), run id, finding id, rule id and expiry, and the entry ids of those that match no call or whose run's record cannot be read (unheld_entries, unread_entries), and under approvals.authority: signed the subject and key id of the operators who signed the stop list's header and the route. No metric label carries an identifier, a digest or free text; pipeline_blocks_total is labelled with a reason code (reference/metrics)
    Who can read it
    anyone who reaches health.address, which takes no credential; health.socket, the plane's account and health.socket_uid

  • the observation log, observe import --log

    What
    per observation its source and trust, its times, the tool name and server address it names, and its correlation ids; per connection from a proxy's log, the host, port, method, status, byte counts and the caller as the proxy wrote it, which can be an address or a user name; never a prompt, an output, reasoning, or a member of the proxy's line the descriptor does not map, such as a path, query, header or body
    Who can read it
    the operator's account: the directory is owner-only and the log 0600

  • the findings log, supervise --findings

    What
    per finding the tenant, project, procedure, rule, verdict and the ids of the events and observations it cites
    Who can read it
    the operator's account: the directory is owner-only and the log 0600

  • notify's state, notify --state

    What
    the keys delivered and the digest of the findings log's first line
    Who can read it
    the operator's account: owner-only, files 0600

  • the program notify runs

    What
    each alert finding's record, one JSON line on its standard input
    Who can read it
    that program, and wherever it sends it

  • the plane's log, on stderr

    What
    messages with ids such as request_id, execution_id and an upstream's name, and error text, never an upstream's or a collector's URL past its scheme and host, an upstream's error message, which is logged by its code, nor a transport error's text, which is logged by its type; header values are never printed
    Who can read it
    wherever the operator sends stderr

The upstream server receives the authorized arguments, as it would without the plane. A plane in OBSERVE sends the proposed ones.

How long records stay

  • a spool segment

    Removed when
    every record in it is accepted by the collector or moved to quarantine.log
    What the operator does
    nothing; evidence.max_bytes bounds what waits

  • quarantine.log in the spool

    Removed when
    when an operator drains it; the plane never removes it, and its bytes count against the budget until then
    What the operator does
    stop the plane, then guardana-gateway spool drain <dir> <out>, which writes every record to a new file before it empties the quarantine

  • the trail segments

    Removed when
    when an operator runs prune on sealed segments; at --max-bytes the collector takes nothing more and the plane blocks material calls
    What the operator does
    stop collect, then guardana-gateway prune --through <n> <dir>, which keeps each segment's tombstone: its lines, bytes and the digests of its first and last line

  • an approval record and its projection

    Removed when
    once its approval has expired, whether it was consumed or not, by a sweep at a plane's start and every quarter of approvals.ttl while it runs, and when the plane settles a hold it lost
    What the operator does
    nothing; a sweep that fails is logged and counted under approvals.sweep in /healthz, and a directory left to grow refuses holds at approvals.max_records

  • a ledger mark

    Removed when
    once it is older than approvals.ttl, by the same sweeps
    What the operator does
    nothing; the ledger refuses a mark past approvals.max_records

  • a run record and its root's state

    Removed when
    when an operator prunes a tree whose every run expired
    What the operator does
    guardana-control runs prune --expired-before <time> --archive <dir> <runs-dir>, which copies the tree into a new archive first

  • a hold journal entry

    Removed when
    when its trail can take nothing more
    What the operator does
    nothing

  • a pause entry

    Removed when
    when an operator removes it; the file keeps no history
    What the operator does
    nothing

  • a stop list's line

    Removed when
    never: lines are appended, and a lift ends a stop without removing it; a list is refused past 4 MiB or 20 000 lines
    What the operator does
    start a new list with stops init --carry, which keeps every unlifted stop, and restart the plane

  • the collector's copy, the log

    Removed when
    as the operator's systems keep them
    What the operator does
    the operator's retention

  • the observation log and the findings log

    Removed when
    never: neither is rotated or pruned, and each is refused past 1 GiB
    What the operator does
    move the directory aside and start a new one

  • notify's state

    Removed when
    never
    What the operator does
    delete it; notify --init on a new state delivers every alert again

  • a dev state directory

    Removed when
    never: it is left behind when dev stops
    What the operator does
    delete it

No command finds or deletes the records about one person. A plane without an authenticator records one configured principal for every call, so a person's identity enters a record through what the operator configured, what an approver or an operator typed, or what a call names: a resource id, a URI, a tool or prompt name, the client's reported name.

Nothing goes to the project

The binaries connect only to addresses the operator configures: the upstreams, the collector, the decision point and its proxy, and, for scenario run, the plane it tests. No address of the project or its authors is built into them, and they send no usage data, crash report or update check.
