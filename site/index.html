Decide which MCP tool calls your AI agents can run.

Watch what they do, and step in only where you allow it.

Put a local gateway between your MCP client and its servers. A signed policy decides each tool call: it runs, it is blocked with its reason, or that exact call waits for one approval. Each decision is recorded with the policy version that made it. The experimental gateway sees only the calls routed through it, and the caller's identity comes from its configuration, not from a login. Do not deploy this as a security boundary.

When to use it

Put a decision between the agent and the consequence

For engineers connecting MCP tools and operators reviewing what a run did. Start with a call you need to control, then inspect its decision and evidence.

01

A write needs approval

A tool can change a record or delete production data. Use the tested starter policy to require approval for writes and deny deletes in an environment named prod. An approval expires and permits that exact call once.

Start from a tested policy

02

A tool changes after review

A tool definition no longer matches the fingerprint you classified. When the gateway refreshes its manifest, that tool becomes unclassified and its calls are blocked in an enforcing mode. This checks the definition, not the server's implementation.

How classification is bound

03

A denied refund is tried another way

The supervisor finds a retry through another tool on the same resource. Run the refund example, inspect the finding and stop that run's later calls through a signed route. Supervision and reaction run when you invoke them.

Follow the refund example

What it does

It intercepts a consequential action before it happens

It returns one of five verdicts. In a mode that enforces, they mean:

  • ALLOW

    The action proceeds.

  • DENY

    The action is blocked.

  • REQUIRE_APPROVAL

    This exact action runs only after an approval.

  • ALLOW_WITH_OBLIGATIONS

    The action proceeds under conditions, enforced unless advisory.

  • INDETERMINATE

    The decision could not be made. It is never an allow.

No language model grants permission. Prompt and tool content capture is off by default, and hidden model reasoning is never stored.

01

Intercept

The enforcement point sits between an agent and its MCP servers. It enforces the verdict except in OBSERVE; APPROVE and a pause can be stricter.

guardana-gateway run --config <file>

02

Decide

The built-in policy engine decides from signed policy bundles. An external decision point (PDP) can veto over AuthZEN but cannot grant. An approval lets one exact action run once, before it expires.

guardana-control policy sign --key <file> --out <file> <document>

03

Record

The evidence record names the configured principal and agent, the action, what was decided, which policy version decided it, how the call ended, and a hash of any answer it could encode, never its content.

guardana-gateway trail <file>

Architecture

How a call is decided today

The enforcement point sits between an agent and its MCP servers and consults the built-in policy engine. An external decision point (PDP) can veto over AuthZEN but cannot grant (experimental).

The enforcement point is the only component this project adds to the request path. Evidence goes to a local spool before export, so decisions do not wait for the exporter.

ROADMAP.md

Where it is going

Further work is planned in the roadmap. MCP is the first of several channels through which it sees what agents do. Today it keeps an agent's runtime traces as testimony: what the runtime says the agent did, never proof. It maps which declared paths a gateway enforces. It checks one run against its procedure and the exceptions the procedure allows, with the run's children where the procedure says so. It draws that run as a page, hands its alerts to a program, and stops one run on a confirmed finding where the operator allowed it. Planned next: sensors the agent cannot influence, such as the proxies its traffic passes through, and alerts to the tools an operator already watches.

Related project: Guardana

Guardana is a separate open-source project that verifies AI systems before and after deployment: it scans artifacts, probes endpoints and reads recorded traces, outside the request path. Guardana Control decides each call inside it.

The two are independent: neither needs the other to build, run or be useful.
