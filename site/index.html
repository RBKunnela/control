Open source · Experimental alpha

Supervise your AI agents. Decide what runs.

An open-source AI agent supervision framework that checks recorded runs against procedures and uses policy to decide connected actions. Start with the alpha; explore connected observation and reaction in the 1.0 goal.

Today: an experimental MCP gateway, signed policies, AuthZEN API vetoes, an Enforcement API for your own tools, runtime trace imports and supervision you invoke for one run. Caller identity is configured, and coverage has gaps. Do not deploy this as a security boundary.

The 1.0 goal

Observe the paths. Supervise the run. React within your authority.

The complete 1.0 target is planned in the roadmap. Follow actions from proposal to known or uncertain outcome across connected tools, APIs, runtimes, network and process sources. Compare them with procedures and permissions, then respond within the operator's scope.

The alpha has exact-action approvals, pause and a stop of one run. You invoke supervision and reaction; there is no continuous supervisor. Authenticated operator review, wider stop scopes and additional delivery routes belong to the 1.0 target. Read the product model and current limits.

When to use it

Start with a call, then inspect the run

These examples work in the alpha. Connect an MCP tool, add your existing authorization service, or check what a run did against its procedure.

01

A write needs approval

A tool can change a record or delete production data. Use the tested starter policy to require approval for writes and deny deletes in an environment named prod. An approval expires and permits that exact call once.

Start from a tested policy

02

Your authorization service can veto

Ask an external PDP through the AuthZEN API for the calls your signed policy routes there. It can veto a local permission and never widen it. An unavailable or unreadable answer blocks those calls in an enforcing mode; OBSERVE records the decision and lets them run.

Connect an AuthZEN veto

03

A denied refund is tried another way

The supervisor finds a retry through another tool on the same resource. Run the refund example, inspect the finding and stop that run's later calls through a signed route. Supervision and reaction run when you invoke them.

Follow the refund example

What it does

It intercepts a consequential action before it happens

It returns one of five verdicts. In a mode that enforces, they mean:

  • ALLOW

    The action proceeds.

  • DENY

    The action is blocked.

  • REQUIRE_APPROVAL

    This exact action runs only after an approval.

  • ALLOW_WITH_OBLIGATIONS

    The action proceeds under conditions, enforced unless advisory.

  • INDETERMINATE

    The decision could not be made. It is never an allow.

No language model grants permission. Prompt and tool content capture is off by default, and hidden model reasoning is never stored.

01

Intercept

The enforcement point sits between an agent and its MCP servers. It enforces the verdict except in OBSERVE; APPROVE and a pause can be stricter.

guardana-gateway run --config <file>

02

Decide

The built-in policy engine decides from signed policy bundles. An external decision point (PDP) can veto over AuthZEN but cannot grant. An approval lets one exact action run once, before it expires.

guardana-control policy sign --key <file> --out <file> <document>

03

Record

The evidence record names the configured principal and agent, the action, what was decided, which policy version decided it, how the call ended, and a hash of any answer it could encode, never its content.

guardana-gateway trail <file>

Architecture

How a call is decided today

The MCP gateway holds the tool connection and consults signed local policy. An external PDP can veto over the AuthZEN API (experimental). Its question carries action metadata, never arguments or their hash.

Evidence goes to a local spool before export, so decisions do not wait for the exporter. A configured external veto adds its own bounded wait. The experimental Enforcement API serves a different role: custom tools ask Control before acting, and a cooperating client enforces the answer. The three API roles

Related project: Guardana

Guardana is a separate open-source project that verifies AI systems before and after deployment: it scans artifacts, probes endpoints and reads recorded traces, outside the request path. Guardana Control observes agent runs and decides consequential actions on connected enforcement paths.

The two are independent: neither needs the other to build, run or be useful.
