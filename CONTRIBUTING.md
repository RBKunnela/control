# Contributing

Thank you for looking at this project. It is alpha, with an `experimental`
gateway, so the most useful contributions right now are to the contracts, the
tests and the decisions, not to features.

Read [AGENTS.md](AGENTS.md) first. It is the working law of this repository and
it is short.

## From a clean machine to a green gate

```bash
git clone https://github.com/guardana/control.git
cd control
make bootstrap
make quality
```

`make bootstrap` compares every binary tool the gate needs with its pin in
`scripts/tool-versions.env`, installs a missing one where it can, and fails on
a mismatch. `go.mod` pins Go and the Go tools. A tool that
cannot be installed is a failure, never a skipped step.

`make quality` is the whole gate, and `ci.yml` runs exactly that target on
your pull request. Use `make quality-quick` while you work; running the whole
gate yourself first saves a round trip.

## Before you write code

Open an issue first for:

- a new adapter, sensor or detector, so the interface is agreed before the work;
- anything that adds a public dependency or widens the public Go surface;
- anything that changes what an existing verdict means.

Write an architecture decision record, in `docs/adr/`, for:

- authorization semantics: a verdict, precedence, the fail-closed table, what
  an approval binds to;
- a public contract, including the wire schemas and the canonical digest;
- the repository layout rule and what the decision path may import;
- licensing and release posture.

Copy `docs/adr/0000-template.md` to the next free number and open the pull
request with `Status: proposed`; the record is part of the change.

A small fix needs neither. Send it.

## Sign off your commits

Every commit carries a Developer Certificate of Origin sign-off:

```bash
git commit -s
```

This adds a `Signed-off-by` line. By adding it you state that you wrote the
contribution or otherwise have the right to submit it under the project
licence, and that you are willing to have that statement recorded in the public
history. The full text is at
[developercertificate.org](https://developercertificate.org/). There is no
contributor licence agreement.

## Commit messages

Commit subjects and pull request titles follow
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/),
`type(scope): summary`. The type is one of `feat`, `fix`, `docs`, `test`,
`refactor`, `perf`, `build`, `ci`, `chore` or `revert`, and a `!` after the
scope marks a breaking change. The scope is optional and names the area, such
as `gateway` or `policy`. The summary is imperative, without a trailing period,
and the whole subject fits in 72 characters. The body says why, wrapped at 72
columns:

```text
fix(gateway): refuse an upstream redirect

A redirect could take an allowed call to a host the configuration does
not name. The client now returns the redirect as an error.

Signed-off-by: Your Name <you@example.com>
```

Pull requests are squash-merged, so the title becomes the commit on `main`. A
workflow checks the title and the sign-off of each commit that adds a change,
except one Dependabot wrote in a pull request it opened.

## Shape of a pull request

- One pull request is one coherent change. If the title needs an "and", split
  it.
- Aim for under 500 changed lines. Above 800, say in the description why it
  could not be split.
- Keep generated and mechanical changes in their own commits, separate from
  changes that alter meaning, so a reviewer can read the part that matters.
- Give it a title in the commit message form above.
- Describe how you tested it, with the command you ran and what it printed.
  "Should pass" is not a result.
- Update the documentation in the same change, or say why none applies.

A change that touches any of authorization semantics, identity and delegation,
approval binding, cryptography, a wire schema with security meaning, redaction,
release signing or workflow security needs two independent approvals. With one
maintainer the project cannot supply them on its own, so your change waits
for a second maintainer or an invited reviewer, except as
[GOVERNANCE.md](GOVERNANCE.md) says.

Only maintainers merge, once the review and the required checks pass.

## How the documentation is written and checked

Every page under `docs/`, except a decision record, opens with frontmatter:
`title` (its one heading), `summary`, `type`, `covers` (globs of the code whose
change makes the page suspect) and, on a rendered page, `generated`. The
directory fixes the type, and `docs/docs.json` holds each type's word budget.
`make docs-check` refuses a page that breaks any of this, a dead link, or a
"supports", "provides" or "integrates with" claim with no status label.

A reference whose source is code is rendered by `make docs-gen` and pinned by a
test, so a hand edit fails the gate; a page pinned by a `go test` is
regenerated by hand from what that test prints. Before opening a pull request,
run `go run scripts/docs-impact.go --range main..HEAD` and reread every page it
names.

## Tooling assistance

Tooling that helped you write a contribution changes nothing about the bar it
is held to. You own its correctness, its licensing and your sign-off. Review
what you submit as if you had typed every line, because to the project you
did.
